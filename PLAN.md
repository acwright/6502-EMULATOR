## Phase 1 — WAI and STP actually halt the processor — **done**

Landed with one deviation from the work list below: `irqTrigger()` does *not*
clear `waiting`. A new `CPU.releaseHalt()` tests the IRQ line at the wake point
and services the interrupt there instead. Clearing the flag in `irqTrigger()`
would have let `tick()` decode and execute the instruction *after* the `WAI`
before the existing post-decode IRQ check fired, pushing a return address of
`WAI+2`.

### The current state

Both opcodes are already decoded — `WAI` at `$CB` and `STP` at `$DB` in the
instruction table ([CPU.ts:1456](src/core/CPU.ts#L1456),
[CPU.ts:1473](src/core/CPU.ts#L1473)), both present in the disassembler's
[OpcodeTable.ts:270](src/debug/OpcodeTable.ts#L270) and covered by
[W65C02S.test.ts](src/tests/W65C02S.test.ts). So the gap is not the opcode
space; it is the semantics. The two bodies at
[CPU.ts:1140-1154](src/core/CPU.ts#L1140-L1154) are placeholders that set
`cyclesRem = 0xFF` and then let execution run straight on. A program that ends
in `STP` keeps executing whatever follows it, and `WAI` is a 255-cycle delay
that ignores interrupts entirely — which is precisely backwards, since the
reason to write `WAI` is to sleep until one arrives.

The existing tests assert the placeholder behaviour (`expect(cpu.pc).toBe(0x8001)`
plus "consumes cycles" in [CPU.test.ts:1975-2005](src/tests/CPU.test.ts#L1975-L2005)
and the `executes WAI from $CB` case in `W65C02S.test.ts`). Those tests get
rewritten in this phase, not preserved.

### Target semantics (W65C02S)

- **`WAI` ($CB, 3 cycles)** — pulls RDY low and stops the processor after the
  instruction. It wakes on IRQ, NMI or RESET. If `I` is set, the interrupt is
  *not* serviced: execution resumes at the instruction after `WAI`. If `I` is
  clear, the interrupt is serviced normally and execution resumes in the
  handler. `PC` has already advanced past the `WAI` byte either way, so the
  return address is correct.
- **`STP` ($DB, 3 cycles)** — stops the clock to the processor. Only RESET
  restarts it. Interrupts do not.

The important detail for this machine: PHI2 is generated by the board's 16 MHz
oscillator divider, not by the CPU ([Machine.ts:52-58](src/core/Machine.ts#L52-L58)).
So a halted CPU must not stop the I/O cards — the RTC has to keep counting or a
`WAI` waiting on its interrupt would never wake. `Machine.tickIO()` keeps running
exactly as now; only `CPU.tick()` becomes inert.

### Work

1. **`CPU`** — two new fields, `waiting` and `stopped` (public, so the host and
   the debug layer can see them).
   - `WAI()` sets `waiting = true`; `STP()` sets `stopped = true`. Neither
     touches `cyclesRem` beyond the instruction's own 3 cycles.
   - `tick()` ([CPU.ts:145](src/core/CPU.ts#L145)) returns early when
     `stopped`, or when `waiting` and no interrupt line is asserted. Cycles
     still accrue on `this.cycles` while halted so cycle budgets and
     `wait.for {cycles}` keep measuring wall time honestly — decide this
     explicitly and comment it, because a frozen counter would hang every
     timeout in the debug protocol.
   - `irqTrigger()` clears `waiting`. When `I` is set the existing `irq()` early
     return already does the right thing — resume without servicing — but that
     path currently only runs from inside `tick()`, so the wake check has to
     happen before the `cyclesRem == 0` decode.
   - `nmi()` clears `waiting`.
   - `reset()` clears both, and is the only thing that clears `stopped`.
2. **Snapshots** — add `waiting` and `stopped` to `serialize()` /
   `deserialize()` ([CPU.ts:209-243](src/core/CPU.ts#L209-L243)). A snapshot
   taken mid-`WAI` that restores into a running CPU would otherwise silently
   change behaviour. Older snapshots lack the keys; `readBoolean` needs a
   default, or read them defensively.
3. **`Session`** — a `STP`'d machine currently burns host CPU forever in
   `run()`, and `step()` / `stepOverOrOut()` spin to `STEP_CYCLE_LIMIT`
   (50 M cycles) before giving up. Emit
   `{ kind: 'trap', detail: 'stp' }` — the `trap` variant already exists at
   [Session.ts:27](src/debug/Session.ts#L27), so nothing in the protocol union,
   the CLI formatter or `DEBUG-PROTOCOL.md` has to change shape — and pause the
   scheduler. `WAI` is *not* a stop: it is normal program behaviour and the
   machine is still live.
4. **Headless host** — `6502 run` should end when the CPU stops, with a distinct
   reason in the `--json` line rather than running out the `--timeout`. Check
   how `HeadlessHost` consumes stop reasons and thread `stp` through to the exit
   reason.
5. **UI** — the machine being halted is invisible today. Smallest useful signal:
   the store exposes a `isHalted` computed from `machine.cpu.stopped`, and
   `ControlBar` shows it on the Run/Stop button's title (a halted machine needs
   Reset, not Run). Keep it to that; a full status LED is scope for another
   release.

### Tests

- Replace the two placeholder blocks in `CPU.test.ts`.
- `WAI` with `I` set: assert the CPU does not advance across many ticks, then
  `irqTrigger()` and assert it resumes at `pc+1` *without* pushing to the stack.
- `WAI` with `I` clear: assert it vectors through `$FFFE` and that the pushed
  return address is the instruction after `WAI`.
- `WAI` woken by `nmi()`.
- `STP`: the CPU never advances again, no interrupt wakes it, `reset()` does.
- Machine-level: `runCycles()` past a `STP` still ticks the I/O cards (assert
  the RTC advanced), and `machine.cycles` still counts.
- Snapshot round-trip through a `WAI`.
- Session: `run()` on a program ending in `STP` stops with
  `{ kind: 'trap', detail: 'stp' }`; `step()` over a `STP` does not hang.

`npm run typecheck`, `npm test`, `bash examples/run-all.sh`, then commit to
`main`. No need to ask.

## Phase 2 — Mute button

### Why it also fixes the web audio confusion

On the web the AudioContext cannot start without a user gesture, so
`armAudioOnFirstGesture()` ([useAudio.ts:246](src/renderer/src/composables/useAudio.ts#L246))
takes the first click or keypress of any kind. Until that happens the emulator is
running with nowhere to send its samples, and there is nothing on screen saying
so — the machine looks broken rather than un-gestured. A mute button gives that
state somewhere to live: it renders muted until the context is actually running,
so the first page load reads "sound is off, click me" instead of silence with no
explanation.

### Design

Mute at the host output, never in the SID. `Sound`'s `masterVolume`
([Sound.ts:256](src/core/IO/Sound.ts#L256)) is emulated register state that
programs read and write; muting there would corrupt it. Nor should we stop
calling `pushSamples` — the drift controller
([useAudio.ts:117](src/renderer/src/composables/useAudio.ts#L117)) steers on
queue depth and would pull the emulator's sample rate to the `MAX_DRIFT` rail
while the queue sat empty. Insert a `GainNode` between `workletNode` and
`ctx.destination` and set its gain to 0 or 1. Everything upstream is unchanged.

**The icon reflects whether sound is actually audible right now, never the
stored preference on its own.** This is the rule the whole button hangs on, and
it is what makes the web case stop being confusing:

```
showsMuted = !audioReady || muted
```

`audioReady` is the existing `globalAudioReady` ref
([useAudio.ts:72](src/renderer/src/composables/useAudio.ts#L72)), which is set
only after `waitForRunningGraph()` has watched `ctx.currentTime` actually
advance ([useAudio.ts:141](src/renderer/src/composables/useAudio.ts#L141)) —
a stricter and more honest signal than `ctx.state === 'running'`, which Chrome
reports before the output device has opened.

So a browser refresh with `muted: false` in storage still renders the muted
icon, because no sound can come out until the AudioContext exists. Deriving it
this way rather than hardcoding "always start muted on the web" also handles the
case where a gesture is *not* required: Chrome's Media Engagement Index, or a
granted sound permission, can let the context start immediately on a
frequently-visited site, and then the icon correctly shows unmuted from the
first frame. One expression, right in both directions.

Four states on one button:

| State | Icon | Title | Click does |
|---|---|---|---|
| Audio not started, preference unmuted | `SpeakerXMarkIcon`, dimmed | "Click to enable sound" | `initAudio()`, gain to 1 |
| Audio not started, preference muted | `SpeakerXMarkIcon`, dimmed | "Click to enable sound" | `initAudio()`, gain to 1, persist unmuted |
| Running, unmuted | `SpeakerWaveIcon` | "Mute" | mute |
| Running, muted | `SpeakerXMarkIcon` | "Unmute" | unmute |

The two pre-gesture rows look identical and behave identically — clicking a
button that reads "muted" means "give me sound" whatever was stored last time.
They differ only in what gets written back. The dimming and the different title
are what distinguish "no audio yet" from "deliberately muted", since the icon
alone cannot.

Note that `armAudioOnFirstGesture()`
([useAudio.ts:246](src/renderer/src/composables/useAudio.ts#L246)) means the
context often starts from some *other* gesture — a keypress into the machine,
say. When it does, `audioReady` flips and the icon updates itself to whatever
the stored preference says. Nothing extra to wire: the derived expression
already covers it.

### Work

1. **`useAudio`** — module-level `gainNode` and a `muted` ref beside the existing
   `globalAudioReady` ([useAudio.ts:72](src/renderer/src/composables/useAudio.ts#L72)).
   Create the gain node in `start()`, wire `workletNode → gain → destination`
   (replacing the direct `connect` at
   [useAudio.ts:217](src/renderer/src/composables/useAudio.ts#L217)), apply the
   persisted mute state to its initial gain. Export `muted`, `toggleMute()`,
   `setMuted()`.
2. **Persistence** — add `muted?: boolean` to `AppSettings`
   ([types.ts:153](src/shared/types.ts#L153)) and `DEFAULT_APP_SETTINGS`, saved
   through `window.api.settings.set` on Electron. On the web there is no
   settings IPC, so use `localStorage` under the existing key convention (see
   `LS_KEY_NVRAM` in [services/persistence.ts](src/renderer/src/services/persistence.ts#L13)).
   The stored value is a *preference*, not a state — it decides the gain node's
   initial value once the graph exists, and it never decides what the icon
   shows. Comment that at the read site; a future reader who wires the icon
   straight to it will reintroduce exactly the confusion this phase removes.
3. **`ControlBar`** — add the button next to the frequency toggle
   ([ControlBar.vue:41-48](src/renderer/src/components/ControlBar.vue#L41-L48)),
   using `SpeakerWaveIcon` / `SpeakerXMarkIcon` from `@heroicons/vue/24/solid`.
   The icon binds to the derived `!audioReady || muted`, never to `muted` alone.
   Clicking when audio has not started must `await initAudio()` first — the same
   thing `toggleRun` already does at
   [ControlBar.vue:122](src/renderer/src/components/ControlBar.vue#L122).
4. **Keyboard shortcut** — optional, and only if it does not collide with the
   emulated keyboard, which captures nearly everything in
   [useKeyboard.ts](src/renderer/src/composables/useKeyboard.ts). A modifier
   combination or nothing at all.
5. **README** — deferred to Phase 4, which does the whole documentation pass in
   one place so it cannot end up half-applied across three commits.

### Tests

The audio path is browser-only and the Jest project is `testEnvironment: 'node'`
with coverage scoped to `src/core`, `src/debug`, `src/host`
([jest.config.cjs](jest.config.cjs)) — there is no component test harness here
and this phase should not introduce one. Verify by hand on both builds.

`npm run dev` (Electron) — `initAudio()` is awaited before the machine starts
([App.vue:116](src/renderer/src/App.vue#L116)), so the button should settle to
the stored preference within the first moment of the window opening; it reads
muted until then, which is accurate rather than a glitch. Toggling works, and
the preference survives a restart.

`npm run build:web && npm run preview:web` — the case this phase exists for:

- Fresh load with nothing stored: reads muted, dimmed, "Click to enable sound".
- Click it: audio starts, icon goes to unmuted, the BIOS beep is audible.
- Reload: **still reads muted** despite `muted: false` being stored. This is the
  check to make deliberately — it is the behaviour that is easy to regress and
  the whole reason the icon is derived rather than bound.
- Click it again: unmutes immediately, no second-guessing.
- Mute deliberately, reload, click to start audio: comes up silent, matching the
  stored preference, with the icon staying muted throughout.
- Start audio via some other gesture — press a key into BASIC instead of
  touching the button — and confirm the icon flips on its own to whatever was
  stored.

## Phase 3 — Embeddable in HTML

### Shape

A second page in the same web build, loaded in an `<iframe>`:

```html
<iframe src="https://acwright.github.io/6502-EMULATOR/embed.html?prg=game.prg&autostart=1"
        width="640" height="520" allow="autoplay; gamepad"></iframe>
```

A separate entry rather than a query flag on the main app, because the embed
wants a different component tree (no settings panel, no serial, no CLI shim, no
persistence by default) and shipping that as dead code behind a flag would make
both harder to reason about. The two share everything below the component
layer — the store, the composables and the whole of `src/core`.

Note that `frame-ancestors` is not set on the current page CSP
([index.html](src/renderer/index.html#L6)) and GitHub Pages sends no
`X-Frame-Options`, so framing already works; nothing has to be relaxed to allow
it. The `connect-src 'self'` directive *does* block fetching a program from
another origin, which matters below.

### Work

1. **Entry point** — `src/renderer/embed.html` + `src/renderer/src/embed.ts` +
   `src/renderer/src/EmbedApp.vue`. Add both HTML files as Rollup inputs in
   [vite.web.config.ts](vite.web.config.ts) so `dist/web/` gets `index.html` and
   `embed.html` side by side. The Electron build is untouched.
2. **`EmbedApp.vue`** — `VideoCanvas` plus an optional compact control bar
   (run/stop, reset, mute, fullscreen). Reuses `useKeyboard`, `useJoystick`,
   `useAudio`; skips `usePersistence`, `useSerial`, `useDebugBridge` unless
   asked for.
3. **URL parameter API** — parsed in one place (`src/renderer/src/embed/params.ts`)
   so it is testable as plain TypeScript under the existing Jest setup:

   | Param | Default | Meaning |
   |---|---|---|
   | `rom` | bundled BIOS | URL of a ROM image |
   | `cart` | — | URL of a cartridge |
   | `prg` | — | URL of a `.prg` / `.bas`, loaded at `$0800` |
   | `bin` | — | `ADDR=url`, repeatable |
   | `autostart` | `1` | boot on load |
   | `autotype` | — | text sent to the console after boot (e.g. `RUN\r`) |
   | `controls` | `minimal` | `full` \| `minimal` \| `none` |
   | `freq` | `1` | 1 or 2 MHz |
   | `muted` | `1` | start muted (browsers block autoplay in iframes anyway) |
   | `persist` | `0` | opt in to IndexedDB CF/NVRAM persistence |
   | `cf` | — | URL of a CF image |

   Unknown parameters are ignored rather than fatal, so the DOCS site can add
   ones a pinned emulator version does not know about yet.
4. **Cross-origin loading** — a `prg` on itch.io's CDN needs both CORS on that
   host and a `connect-src` that permits it. Relax the embed page's CSP to
   `connect-src 'self' https:` (the embed fetches program data and nothing
   else), and accept a same-origin-only fallback: also support `prg64=`, a
   base64 payload in the URL, so a small program can be embedded with no network
   fetch at all. That is the form the DOCS site will want for inline samples.
5. **Focus and key capture** — inside an iframe, `window` key listeners only
   fire when the frame has focus, which is already the behaviour we want. What
   is missing is a way in and a way to tell: a focusable wrapper (`tabindex="0"`),
   a visible focus ring, and a "click to start" overlay before first focus. The
   `preventDefault()` calls in
   [useKeyboard.ts:24](src/renderer/src/composables/useKeyboard.ts#L24) must
   stay conditional on having focus so arrow keys and space still scroll the
   host page when the emulator is not being used.
6. **Persistence off by default** — the store hardcodes a 256 MB CF card
   ([stores/emulator.ts:20](src/renderer/src/stores/emulator.ts#L20)) and
   `Storage` allocates it eagerly
   ([Storage.ts:150](src/core/IO/Storage.ts#L150)). Two embeds on one docs page
   would be half a gigabyte of `Uint8Array` and would share one IndexedDB store.
   The embed passes a much smaller size (the `Storage` constructor already takes
   one) and skips `usePersistence` entirely unless `persist=1`.
7. **`postMessage` control API** — so the DOCS site can put a "Run this" button
   beside a code block. Inbound: `{ type: '6502:load', kind: 'prg', data }`,
   `'6502:run' | 'pause' | 'reset' | 'powerCycle' | 'setMuted' | 'type'`.
   Outbound: `'6502:ready'`, `'6502:stopped'`, `'6502:serial'`. Validate
   `event.origin` against an `origins=` parameter, defaulting to accepting any
   origin only when the parameter is absent — document that trade-off rather
   than leaving it implicit.
8. **Optional `embed.js` loader** — a tiny script that turns
   `<div data-6502-prg="…">` into a correctly-sized iframe. Convenience only;
   drop it if the phase is running long, since the raw `<iframe>` works without it.
9. **Docs** — `docs/EMBEDDING.md` (parameters, `postMessage` API, CORS/CSP
   notes, sizing) and `examples/embed.html` as a runnable demo page exercising
   both the URL API and `postMessage`. `EMBEDDING.md` is the reference and
   belongs with this phase; the README section pointing at it is Phase 4.

### Tests

- `params.ts` parsing (defaults, unknown keys ignored, `bin` repetition,
  malformed values) as Jest unit tests — add `src/renderer` to
  `collectCoverageFrom` only if the file lands somewhere the `moduleNameMapper`

- Manual: `npm run build:web && npm run preview:web`, then open
  `examples/embed.html` against the preview server — two embeds on one page,
  keyboard focus moving between them, audio unmuting per-frame, `postMessage`

### Commit

`npm run typecheck`, `npm test`, `bash examples/run-all.sh`, plus
`npm run build:web` — this phase adds a Rollup input, so a build that no longer

## Decisions worth making before Phase 1 and Phase 3 start

- **Do halted cycles still count?** Phase 1 assumes yes — `machine.cycles` and
  `cpu.cycles` keep advancing through `WAI` and `STP`, because every timeout and
  cycle budget in the debug protocol is denominated in them. The alternative
  (freeze the counter, matching a real stopped clock more literally) would hang
  `--timeout` and `wait.for`. Going with the former unless you want otherwise.
- **`STP` as a stop reason.** Reusing `{ kind: 'trap', detail: 'stp' }` avoids
  touching the protocol's `StopReason` union and every consumer of it. A
  dedicated `{ kind: 'halt' }` would be cleaner to switch on but is a
  protocol-version-visible change.
- **Embed `postMessage` origin default.** Accepting any origin when `origins=`
  is absent is what makes the itch.io case work without configuration; it also
  means any page framing the emulator can drive it. The emulator has no
  credentials and no access to the host page, so the exposure is limited to
  controlling the emulated machine — acceptable, but it should be a deliberate
  call rather than a default nobody chose.
