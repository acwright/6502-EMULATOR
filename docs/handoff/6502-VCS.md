# What emulator 3.4 guarantees to the Flash Cart

The AC6502 VCS is getting a banked flash cartridge, and four independent things
have to agree bit for bit about it: this emulator, the 6502-PICOCALC port,
6502-DEV's DB Emulator, and the `6502-flash` host tool that drives the Flash
Helper. **6502-VCS `PLAN.md` is the normative copy of all of it** — §1 naming,
§2 the mapper, §3 the flash command set, §4 the `.sav` container — and nothing
here re-decides any of it.

This file is the other direction: what a hardware author can rely on when they
run a cart here before there is silicon, and where this emulator deliberately
stops short of the chip.

Written from emulator `main` at 3.4.0. It is deleted when the Flash Cart
rollout closes.

---

## The oracle is the fixtures, not this emulator

`src/tests/fixtures/cart/` holds byte copies of 6502-VCS
`Firmware/FH Programmer/host/test/fixtures/`:

| File | Bytes | CRC-32 |
|---|---|---|
| `legacy.crt` | 32,768 | `98a4e0fd` |
| `legacy-512K.crt` | 524,288 | `bdaa7346` |
| `banked-128K.crt` | 131,072 | `e0e4f83c` |
| `sample.sav` | 12,316 | `45c4068e` |

They are the shared oracle, and the tests here quote those checksums so a stale
copy fails rather than passing quietly against the wrong bytes. **If one of them
moves, this repository has to be told** — and everything below stops being a
guarantee until it is re-checked.

## The five sizes

Every host takes all five, and refuses anything else with a message naming them:

| Target suffix | Bytes | Part | Mapper |
|---|---|---|---|
| *(none)* | 32,768 | 28C256 / 27C256 | flat |
| `-128K` | 131,072 | SST39SF010A | banked |
| `-256K` | 262,144 | SST39SF020A | banked |
| `-512K` | 524,288 | SST39SF040 | banked |
| `-1M` | 1,048,576 | SST39SF040 ×2 | banked |

**The size decides the mapper and the name never does** (§1 rule 2). A name
whose target suffix disagrees with the byte count is a warning and the cart
loads anyway (rule 3) — `Foo-512K.crt` at 262,144 bytes loads as a 256K cart and
says so.

The 32K ROM cart is not replaced, anywhere. A 32,768-byte `.crt` loads exactly as
it did in 3.3.0, through the same flat path, and the goldens captured from one
did not move.

## What is modelled

- **The bank register.** Write-only at any address in `$E000–$FFFF`, eight bits,
  cleared to 0 by `RESB` — including a *warm* reset, because its `/MR` is on that
  line. Bit 7 is latched and goes nowhere. A value above the part's bank count
  aliases down, because the high address pins are not bonded on a 010A or a 020A.
- **The fixed region.** `$E000–$FFFF` is the primary chip's last 8 KB whatever
  the register holds, vectors included.
- **A write to `$E000–$FFFF` reaches no flash.** `WEB` is not asserted there, so
  it latches the register and is not also a flash write.
- **The JEDEC command set of §3**, over unlock addresses compared as
  `addr & 0x7FFF` — the part decodes only A14–A0 for commands, so CPU `$D555` in
  bank 2 is flash `$5555` with no special-casing anywhere.
- **Program clears bits only.** `new = old & data`. A routine that expects a `0`
  to come back as a `1` without an erase fails here as it would on the part.
- **Software ID**, `$BF` and `$B5`/`$B6`/`$B7` by size.
- **Sector and chip erase**, 4 KB aligned and whole-part.
- **The busy window** — 20 µs for a byte program, 25 ms for a sector erase,
  100 ms for a chip erase, at 1 MHz. See below.
- **U2 on a `-1M` image is the second 512 KB** (§1 rule 4), so the file is linear
  and so is the bank numbering.

## What is not

- **The Flash Helper is not emulated.** There is no serial transport here and no
  programmer; `6502-flash` lives in 6502-VCS and talks to a real board.
- **Open bus reads `$FF`.** Selecting the absent U2 on a one-chip cart reads
  `$FF` for the whole window. That is the rollout's agreed simplification, not a
  measurement, and it is recorded in 6502-DOCS `ACCURACY.md`.
- **The busy window is counted in CPU cycles, not in wall time.** The plan states
  the windows in microseconds at 1 MHz and the machine hands the cart its raw
  cycle count. The ACE runs at 1 MHz only (since 3.5), so a cycle is a
  microsecond.
- **`-1M` has not met silicon**, here or anywhere. Two chips are modelled and
  6502-CRT lays U2 out after `FIXED`; both pass their own tests and neither has
  been burnt. Carry the code; do not claim it.

## The busy window is the part that earns its keep

`DESIGN.md` requires a self-programming routine to run from RAM with interrupts
off, because a busy chip answers **every** read of it — the instruction fetches
in the fixed region and the vector fetches included. An emulator that completed a
program instantly would happily run a routine that hangs on the board.

So it does not complete instantly, and a cart that gets this wrong hangs here
first. `samples/flash-cart/` is the worked example and a golden fixture: it
copies its programming routine into RAM, programs a byte into bank `$0E`, data-
polls `DQ7` until it reads back, and prints both the before and the after byte on
screen. While the chip is busy, reads return status — DQ7 complemented, DQ6
toggling on every read, DQ5 clear — so both standard polling loops terminate.

**If a cart hangs in the emulator at a program or an erase, the first thing to
check is whether the polling loop is executing out of the chip it just made
busy.** It is not a bug here; it is the bug you were going to find on the bench.

## Saves cannot reach a chip

§4's requirement is that a save written while testing must not be able to end up
on a real chip by accident, and the mechanism is that it never enters the image.

- **No host in this repository opens a `.crt` for writing.** Not the CLI, not the
  desktop app, not the web build. There is no flag, no setting and no IPC channel
  that names one. A test asserts a `.crt`'s mtime after a run that programs flash.
- Flash writes accumulate in a sector-granular overlay — 4 KB records, the chip's
  own erase unit — in the container §4 specifies byte for byte. `src/core/CartSave.ts`
  is this emulator's implementation and `sample.sav` is what it is checked against.
- `image_size` and `image_crc` are what make it safe. Rebuild the cart and the
  CRC moves; the loader then reports *"save data belongs to a different build of
  this cart"*, starts the cart without the overlay, and **leaves the file exactly
  where it was**. Nothing here ever deletes a save.
- Where the overlay lives follows what the cart arrived with, not which build it
  is. A cartridge named on the command line has a path, so its saves go to
  `<stem>.sav` beside the `.crt` — which is where `6502-flash merge` would look
  for them. A cartridge chosen through a file picker has no path, so its saves go
  into the browser's IndexedDB under the image's CRC-32.

```sh
6502 run --headless --cart Cart-512K.crt          # saves to Cart-512K.sav
6502 run --headless --cart Cart-512K.crt --no-cart-save
6502 run --headless --cart Cart-512K.crt --cart-save /tmp/scratch.sav
```

A run that never programmed the flash writes no file at all, so an empty save
never replaces a real one.

## Seeing the register from outside

A banked cart is close to undebuggable without this, because `$C000` means a
different 8 KB depending on a register nothing else reports:

```sh
6502 dbg cart              # size, checksum, bank count, the register, the window
6502 dbg cart bank 9       # move the window, as a write to $E000 does
```

Both print what the *board* does with the register rather than what was written
to it: bit 7 latched and ignored, a bank above the part's count aliased down, and
an unfitted U2 reported as reading `$FF` rather than as an error. The same thing
is on the debug protocol as `media.cart` and `media.setBank`, and in
`session.info`.
