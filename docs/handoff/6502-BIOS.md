# What 6502-BIOS wanted from the emulator's second video card — and where it went

Emulator 3.0.0 gave the machine two video cards: the TMS9918A of 2.x, still the
default, and the 6502-PICOVDP of [../VDP-SPEC.md](../VDP-SPEC.md). This file was
written from the emulator side as the list of work that created, or made
possible, in [6502-BIOS](https://github.com/acwright/6502-BIOS).

**6502-BIOS's own `VDP-PLAN.md` has since taken all of it up and shipped it.**
What follows is the record of what was asked and what answered, checked against
6502-BIOS `bd476a8` (tag `v2.0.2`) on 2026-09-17, and then the part that is not
history: how a changed BIOS comes back into this repository.

## Where things stand

- **6502-BIOS.** `v1.x` is cut at `v1.6` and is the TMS9918A line. `main` is 2.x,
  the PICOVDP line, at `v2.0.2`.
- **The emulator.** 3.2.0 is on `main`, with `--vdp tms9918a|picovdp` on
  `6502 run`, headless and windowed. `session.info.vdp` says which card a machine
  has. The PICOVDP implements SPEC draft 0.5, the built-in font included.
- **Bundled ROMs.** The TMS9918A boots `BIOS.bin`, 6502-BIOS tag `v1.6`
  (`8acb4fc`, sha256 `4b4154af…`). Since emulator 3.1.0 the PICOVDP boots
  `BIOS2.bin`; from 3.2.0 that is tag `v2.0.2` (`bd476a8`, sha256 `7a71252d…`).
  [../../assets/roms/README.md](../../assets/roms/README.md) is the record of
  both, digests and all.

**Nothing here was ever needed to boot.** The unmodified 1.x BIOS reaching `OK`
on the PICOVDP was the acceptance test for the whole emulator rewrite, and it is
held there by golden frames on both cards.

## The one thing still open

**6502-BIOS CI pins `EMULATOR_REF: v3.0.1`** (`.github/workflows/ci.yml`). It can
move to `v3.2.0`, which is where flow control on by default and the exact R6551
live. `v1.x` stays on `EMULATOR_REF: v2.7.0`; if it ever moves to 3.x it passes
`--vdp tms9918a`.

## 2.x does not run on a TMS9918A

Settled, and worth keeping: **BIOS 2.x has no TMS9918A support**, and no fallback
path. A 1.x ROM is what a TMS9918A board runs, and the emulator warns when it
sees a 2.x ROM on the wrong card
(`BIOS 2.x needs the PICOVDP card (--vdp picovdp)`).

Register aliasing is the reason. The TMS9918A decodes three register bits, so a
write to `L0SCRY`, register `$14`, lands on register 4, the pattern table base —
a hardware scroll would move the character set out from under the screen.
Likewise `$9C02`/`$9C03` reach the *same* port as `$9C00`/`$9C01` on a TMS9918A,
so "interrupt handlers use port B" holds only on the PICOVDP.

## What was asked for, and what landed

All of the following is in 6502-BIOS 2.x as tagged. The emulator side of each is
in `src/tests/goldens/`, `src/tests/BIOS.test.ts` and the docs named.

| Asked | Where it landed |
|---|---|
| Widen the "nothing reaches the VDP" probe from two ports to four | `tests/probe/no-video-card-nothing-reaches-the-vdp.mjs` watches `$9C00`–`$9C03` |
| Name the card in the test profiles, since a headless `--console video` with no `--vdp` gets the TMS9918A | `tests/run.mjs` runs `--vdp picovdp --flow-control` |
| Retitle the colour-register probe, which said TMS9918 | `tests/probe/color-sets-the-pen-and-the-border.mjs`, beside `color-writes-register-7-once.mjs` |
| Stop saying TMS9918 where the card is a PICOVDP | Done through `Kernal.asm`, `BIOS.inc`, `README.md` and the test helpers; what is left names the TMS9918A deliberately, as the thing the card is not |
| Detect the card before trusting it | The boot probe selects `STAT4`, looks for `$AC`, records `STAT5` in `VDP_FW` and `STAT6` in `VDP_CAPS`, and sets `HW_VID` only if `STAT6` b7 says the built-in font is there. A TMS9918A takes the select as a harmless register 7 write |
| Hardware scroll instead of copying 23 rows through `SCROLL_BUF` | `VID_TOP` and `L0SCRY`, with the scroll origin folded into every cursor calculation |
| Vertical blank, and new Kernal entry points | `WaitVBlank` (`$A0C3`), `VdpSetMode`, `VdpSetPalette`, `VdpLoadFont`, `VdpSetScroll` and the rest, in the reserved slots; BASIC gained `SCREEN`, `VPOKE`, `PALETTE`, `SPRITE`, `LAYER`, `SCROLL`, `VSYNC` |
| Fix the paste deadlock: raising RTS turns the R6551's transmitter off | 6502-BIOS `v1.6` (`8acb4fc`) and `v2.0.1` (`62254c1`) — see below |
| Drop the `xfail` on `a-pasted-program-crunches-without-dropping-input` | Gone; the case passes with flow control on |

### The paste deadlock, in full, because it cost a bench day

Flow control is on by default from emulator 3.2.0 (`6502 run --no-flow-control`
turns it off; `session.info.flowControl`), and the ACIA is modelled as the R6551
the boards carry. On that chip command register bits 3-2 at `00` mean
*transmitter off* as well as *RTS high* — confirmed on the bench on 2026-09-17,
where `POKE 36866,1` on a real board stopped it transmitting mid-reply and hung
it — so TDRE never set and `SerialChrout` spun. Both 1.6 and 2.0 raised RTS
(`$01`) from the IRQ handler once `INPUT_BUFFER` filled and then echoed the next
character, so a long paste into BASIC killed the machine, whatever the terminal
was set to.

The fix: one routine, `ScRts`, owns the command register (RTS up at `$C0`, down
below `$80`, left alone between), and `SerialChrout` lowers RTS around each byte
with `sei` held across the character. The bench then found three more faults
behind it, all fixed in the same tags — the input ring lapped its reader at 256
unread bytes and wiped itself; the IRQ handler read the data register without
checking `RDRF` and stored characters twice; and, since sending means lowering
RTS, every echo let another byte in, so a flooded buffer never recovered.
`ScFlooded` now keeps the console quiet above the high mark instead. On a real
KIM: pastes of 50, 100, 150 and 300 lines (to 14 KB) arrive byte-perfect with the
host honouring RTS, the board answering afterwards; with flow control off it
stays lossy and stays up; and `POKE 36866,1` then `PRINT` prints and leaves the
board alive.

Emulator side: the paste cases in `src/tests/host/HeadlessHost.test.ts` run
against **both** bundled ROMs and assert what the bench says — whole with flow
control on, lines lost and no hang with it off. The chip model is unchanged and
still tested (`ACIA.transmitterEnabled`; `TIC 00 turns the transmitter off` in
`src/tests/BIOS.test.ts` and `src/tests/IO/ACIA.test.ts`).

### The border a first `COLOR` shows

`v2.0.2`, the one change after the flow-control tags. The Text console comes up
on first use, and `InitVideo` writes register 7 with the display off, which a
blanked PICOVDP shows over the whole screen while the font loads. It took the
border from `VID_PEN`, which `VideoSetPen` had not stored yet, so a first
`COLOR 2,5,12` flashed the old pen's background. `VID_BORDER` (`$039C`) now
holds the border the console shows, and the pen and border are stored before the
bring-up. Two behaviour changes follow, both deliberate: a first `COLOR` clears
in its own pen, so border and background agree; and a border given to
`COLOR fg,bg,border` survives a program returning to the Text console.
[../../assets/roms/README.md](../../assets/roms/README.md) has the detail.

## Bringing a changed BIOS back into the emulator

This is the part that is not history. It is the procedure every time 6502-BIOS
tags a new image.

- 2.x is bundled as **`BIOS2.bin`**, at `assets/roms/BIOS2.bin` and
  `src/renderer/public/roms/BIOS2.bin`, and `BUNDLED_ROM.picovdp` in
  `src/shared/vdp.ts` points at it. `BIOS.bin` stays 1.6 for good, for the
  TMS9918A. `src/tests/BundledROM.test.ts` fails if either pair differs, or if
  either digest is not the one recorded. Copy both, then re-pin the digest,
  tag and commit there and in `assets/roms/README.md`.
- The PICOVDP fixtures in `src/tests/goldens/fixtures.js` boot `BIOS2.bin`.
  `src/tests/goldens/bios/` moves whenever the console's own output or timing
  moves; `wizardslab/`'s frames must not, because 2.x's `KernalInit` leaves the
  card in the legacy submode and a cartridge draws its own screen. A change to
  how long `KernalInit` takes moves `vdp-layers/`, which scrolls every frame.
  Run `npm run capture:goldens -- --check` first to see exactly what moved, and
  re-capture in a commit that says why.
- **`src/tests/goldens/tms9918a/` never moves for a 2.x change.** Those goldens
  pin the TMS9918A booting 1.6.
- `src/tests/BIOS.test.ts`, `HeadlessHost.test.ts` and `Snapshot.test.ts` boot
  the bundled ROM; a Kernal change that alters cycle counts to the prompt can
  move numbers there. `npm run replay:traces` covers the recorded sessions.
- A new bundled 2.x image invalidates PICOVDP snapshots taken against the old
  one — the version string has said `v2.0` throughout, so matching is on the
  ROM. Say so in [../MIGRATING.md](../MIGRATING.md).
