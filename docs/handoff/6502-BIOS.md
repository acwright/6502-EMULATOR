# What 6502-BIOS wants from emulator 3.0

The emulator's video card is now the 6502-PICOVDP of [../VDP-SPEC.md](../VDP-SPEC.md).
This is the list of work that change creates, or makes possible, in
[6502-BIOS](https://github.com/acwright/6502-BIOS). It was written from the
emulator side and has not been started in that repository.

**Nothing here is needed to boot.** The unmodified BIOS reaching `OK` on this card
was the acceptance test for the whole emulator branch (`PLAN.md`), and it is held
there by golden frames. It follows that none of this should be done *on* that
branch: an altered BIOS proves nothing about compatibility (`PLAN.md` risk 7).

Line numbers are as of 6502-BIOS `1920a86`. Section numbers (§) are VDP-SPEC's.

---

## Before anything else

### The fact that shapes every item below

A real ACE still has a Pico9918 running as a TMS9918A. The PICOVDP is a
specification for firmware that does not exist yet. So every Kernal change that
uses the new card has to **detect it and fall back** — and on a TMS9918A the
fallback is not optional, because the new registers are not merely absent there.
The TMS9918A decodes three register bits: a write to `L0SCRY`, register `$14`,
lands on register 4, which is the pattern table base. A hardware scroll that ran
unconditionally would move the character set out from under the screen on every
existing board.

Likewise the second port pair: today `$9C02`/`$9C03` reach the *same* port as
`$9C00`/`$9C01`, so "interrupt handlers use port B" is a convention that is only
safe on the new card.

## 1. Should — tests and CI

These are the ones that keep the BIOS's own test suite honest once it runs against
3.0.

**Widen the "nothing reaches the VDP" probe to four ports.**
`tests/probe/no-video-card-nothing-reaches-the-vdp.mjs:21-23` watches `$9C00` and
`$9C01` ("the TMS9918 is two addresses"). The card now answers at `$9C00`–`$9C03`,
so a write to port B on a machine with no video card would pass this test. Watch
all four.

**Bump the emulator the CI builds, when 3.0.0 is tagged.**
`.github/workflows/ci.yml:32` pins `EMULATOR_REF: v2.6.0`. Until that moves, the
BIOS's tests keep running against a TMS9918A, which is correct for today's
hardware and says nothing about the new card. Moving it is when every `tests/probe/`
case first meets the PICOVDP; expect them to pass, since the goldens say the boot
path is unchanged.

**Retitle the colour-register probe.**
`tests/probe/color-sets-the-tms9918-colour-register.mjs` asserts a write to
register 7. That is still exactly right — `COLOR` is register 7 on both cards — but
the name and comments (lines 1–6, 30, 33, 46, 78, 86) say TMS9918.

## 3. Could — detect the card

Everything in §4 and §5 needs this first.

`ProbeVideo` (`Kernal.asm:1548-1579`) writes `$A5` to VRAM and reads it back, which
any card with readable VRAM passes. §16's probe tells the two apart: select
`STAT4` (write `$04` to register `$0F`) and read `$AC` from the status port.

- **Where the answer goes.** `HW_PRESENT` has no free bit (`BIOS.inc:64-71`), so it
  needs a new RAM byte — a card type, or a capabilities copy of `STAT6` (§6).
- **Order matters.** On a TMS9918A the probe's register write lands on register 7
  and changes the screen colours. Run it before `InitVideo`, which writes R7 = `$1F`
  anyway (`Kernal.asm:837`), and the damage is undone for free.
- **Put `STAT0` back afterwards** (§16's listing does), or the next status read
  returns `$AC` instead of the frame flag.
- **Verify in the emulator:** a 3.x build answers `$AC`; a 2.6.9 build is a
  TMS9918A and must take the fallback. Both are one `6502 run --headless` away.

## 4. Could — hardware scroll

§17's headline change. `VideoScrollImpl` (`Kernal.asm:252-336`) copies 23 rows of 40
through `SCROLL_BUF` — about 31,000 cycles, 30 ms at 1 MHz. Writing `L0SCRY` and
clearing one row is under 400 (§17 has the code).

The cost is a scroll origin that every cursor calculation has to fold in. The
places that assume the origin is zero:

- `VideoSetCursorImpl` (`Kernal.asm:183-224`), which computes `Y*40 + X` into
  `VID_CURSOR_ADDR`
- `VideoChroutImpl` and `VideoChroutRawImpl`, which increment `VID_CURSOR_ADDR`
  directly (374–376, 448–450), and their row and column limits (379, 385, 389, 411,
  414, 453, 458, 461)
- `VideoPutCharImpl` (243–247)
- `VideoClearImpl`, which zeroes the address (168–169) — and should reset the
  origin and `L0SCRY` with it

`VideoGetCursorImpl` is the exception: it returns `VID_CURSOR_X` and `VID_CURSOR_Y`,
which stay screen coordinates, so it needs nothing.

The name table address becomes `(origin + Y*40 + X) mod 960`; the origin moves by 40
per scrolled line and `L0SCRY` by 8, wrapping at 192 (§13 wraps the map at the
geometry's own height, which in Text is 192).

**This has a free acceptance test.** A correct hardware scroll draws the same
picture as the software one, so the emulator's `bios/scroll` golden *index frame*
must stay byte-identical while its VRAM image and registers move. Re-capture those
in a commit of their own in the emulator, per `PLAN.md` ground rule 4.

## 5. Could — interrupts, vertical blank, new entry points

**Port B for interrupt handlers.** The Kernal's `Irq` (`Kernal.asm:3159-3209`) never
touches the VDP and nothing in the BIOS brackets VDP work with `sei`/`cli`, so
there is no existing race to fix. The hazard is a *user* handler installed through
`IRQ_PTR` that talks to the card while foreground code is between the two writes of
a command. On the new card that handler can use `$9C02`/`$9C03` and never disturb
the foreground's pointer or flip-flop (§4). Worth writing down as the convention —
with the caveat from the top of this file that on today's card port B *is* port A.

**Vertical blank.** Nothing in the BIOS waits for a frame. `STAT0` b7 is set at the
end of every picture whatever `IRQEN` holds (§6) — and so was the TMS9918A's — so
a `WaitVBlank` entry point works on both cards.

**New Kernal entry points.** §17 suggests set mode, set a palette entry, set layer
scroll, load a tile set, place a sprite, enable a layer.

- The jump table (`Kernal.asm:25-100`) has 32 reserved slots, of which the planned
  v1.6 NVRAM save slots claim 6 (`PLAN.md:282`).
- The ABI is pinned in `tests/fixtures/jumptable.json`; new slots update it.
- Each entry point needs the detection result from §3 and a defined behaviour on a
  TMS9918A — returning carry set is the obvious one.
- BASIC has three video keywords today, `CLS`, `LOCATE` and `COLOR`
  (`BASIC.asm:273-275`, 8257–8285), and no `SCREEN`, `VPOKE` or `SPRITE`. Whether it
  should grow any is a design question this list does not answer.

## Bringing a changed BIOS back into the emulator

- `BIOS.bin` is bundled twice, at `assets/roms/BIOS.bin` and
  `src/renderer/public/roms/BIOS.bin`, and `src/tests/BundledROM.test.ts` fails if
  they differ. Copy both.
- `src/tests/goldens/bios/` will move if the console draws differently. Run
  `npm run capture:goldens -- --check` first to see exactly what moved, and
  re-capture in a commit that says why.
- `src/tests/BIOS.test.ts`, `HeadlessHost.test.ts` and `Snapshot.test.ts` boot the
  bundled ROM; a Kernal change that alters cycle counts to the prompt can move
  numbers there.
