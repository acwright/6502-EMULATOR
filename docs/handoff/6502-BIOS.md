# What 6502-BIOS wants from emulator 3.0

Emulator 3.0.0 has two video cards: the TMS9918A of 2.x, which is the default, and
the 6502-PICOVDP of [../VDP-SPEC.md](../VDP-SPEC.md). This is the list of work the
PICOVDP creates, or makes possible, in
[6502-BIOS](https://github.com/acwright/6502-BIOS). It was written from the
emulator side, and 6502-BIOS's own `VDP-PLAN.md` has since taken it up; once that
plan has absorbed everything here, this file is deleted.

**Where things stand:**

- **6502-BIOS.** `v1.x` is cut at `v1.6` and is the TMS9918A line. `main` is 2.x,
  the PICOVDP line.
- **The emulator.** 3.0.0 is on `main` (tag `v3.0.0`), with `--vdp tms9918a|picovdp`
  on `6502 run`, headless and windowed. `session.info.vdp` says which card a
  machine has. The PICOVDP implements SPEC draft 0.5, the built-in font included.
- **Bundled ROMs.** The TMS9918A boots `BIOS.bin`, 6502-BIOS tag `v1.6`
  (`8acb4fc`, sha256 `4b4154af…`). Since emulator 3.1.0 the PICOVDP boots
  `BIOS2.bin`, which is tag `v2.0.1` (`62254c1`, sha256 `f5fb454b…`).
  6502-BIOS may pin `v3.1.0`.

**Nothing here is needed to boot.** The unmodified 1.x BIOS reaching `OK` on the
PICOVDP was the acceptance test for the whole emulator rewrite, and it is held
there by golden frames on both cards.

Line numbers are as of 6502-BIOS `1920a86`. Section numbers (§) are VDP-SPEC's.

---

## Before anything else

### 2.x does not run on a TMS9918A

That question is settled: **BIOS 2.x has no TMS9918A support**, and no fallback
path. A 1.x ROM is what a TMS9918A board runs.

The register aliasing is the reason 2.x must never run on `--vdp tms9918a`, and
why the emulator warns when it sees one there
(`BIOS 2.x needs the PICOVDP card (--vdp picovdp)`). The TMS9918A decodes three
register bits: a write to `L0SCRY`, register `$14`, lands on register 4, which is
the pattern table base. A hardware scroll would move the character set out from
under the screen. Likewise `$9C02`/`$9C03` reach the *same* port as
`$9C00`/`$9C01` on a TMS9918A, so "interrupt handlers use port B" holds only on the
PICOVDP.

## 1. Should — tests and CI

These are the ones that keep the BIOS's own test suite honest once it runs against
3.0.

**Widen the "nothing reaches the VDP" probe to four ports.**
`tests/probe/no-video-card-nothing-reaches-the-vdp.mjs:21-23` watches `$9C00` and
`$9C01` ("the TMS9918 is two addresses"). The card now answers at `$9C00`–`$9C03`,
so a write to port B on a machine with no video card would pass this test. Watch
all four.

**Pin emulator 3.0.0 and name the card.**

- `main`'s `.github/workflows/ci.yml` pins `EMULATOR_REF: v3.0.0`.
- The `video` profile in `tests/run.mjs` becomes
  `['--console', 'video', '--vdp', 'picovdp']`. **This is required, not tidy:**
  from 3.0.0 a headless `--console video` run with no `--vdp` gets the TMS9918A.
- Add `--vdp picovdp` to the serial profile as well. io8 stays empty either way,
  so it changes nothing today, but it keeps the bundled-ROM choice right if a test
  ever omits `--rom` once 2.0 is bundled for the PICOVDP.
- Confirm the card in a probe with `session.info`'s `vdp`.
- `v1.x` stays on `EMULATOR_REF: v2.7.0`. If it ever moves to 3.x, it passes
  `--vdp tms9918a`.

**~~Raising RTS turns the R6551's transmitter off, so a paste deadlocks
BASIC.~~ Done — 6502-BIOS tags `v1.6` (`8acb4fc`) and `v2.0.1` (`62254c1`).**

Flow control is on by default from 3.2 (`6502 run --no-flow-control` turns it
off; `session.info.flowControl`), and the ACIA is modelled as the R6551 the
boards carry. On that chip command register bits 3-2 at `00` mean *transmitter
off* as well as *RTS high* — confirmed on the bench on 2026-09-17, where
`POKE 36866,1` on a real board stopped it transmitting mid-reply and hung it —
so TDRE never set and `SerialChrout` spun. Both 1.6 and 2.0 raised RTS (`$01`)
from the IRQ handler once `INPUT_BUFFER` filled and then echoed the next
character, so a long paste into BASIC killed the machine, whatever the terminal
was set to.

Option A landed first: one routine, `ScRts`, owns the command register (RTS up at
`$C0`, down below `$80`, left alone between), and `SerialChrout` lowers RTS
around each byte with `sei` held across the character. The bench then found three
more faults behind it, all fixed in the same tags — the input ring lapped its
reader at 256 unread bytes and wiped itself; the IRQ handler read the data
register without checking `RDRF` and stored characters twice; and, since sending
means lowering RTS, every echo let another byte in, so a flooded buffer never
recovered. `ScFlooded` now keeps the console quiet above the high mark instead.
On a real KIM: pastes of 50, 100, 150 and 300 lines (to 14 KB) arrive
byte-perfect with the host honouring RTS, the board answering afterwards; with
flow control off it stays lossy and stays up; and `POKE 36866,1` then `PRINT`
prints and leaves the board alive.

**Emulator side, done here:** `BIOS.bin` is `v1.6` (sha256 `4b4154af…d8c56`) and
`BIOS2.bin` is `v2.0.1` (sha256 `f5fb454b…0d97b`), and the paste cases in
`src/tests/host/HeadlessHost.test.ts` run against **both** and assert what the
bench says — whole with flow control on, lines lost and no hang with it off. The
chip model is unchanged and still tested (`ACIA.transmitterEnabled`; `TIC 00
turns the transmitter off` in `src/tests/BIOS.test.ts` and
`src/tests/IO/ACIA.test.ts`). The deadlock caveat is gone from the READMEs,
`docs/AGENTS.md` and `docs/DEBUG-PROTOCOL.md`.

**Still open, for 6502-BIOS:**

- `a-pasted-program-crunches-without-dropping-input` should now pass with flow
  control on, so its `xfail` can go.

**Retitle the colour-register probe.**
`tests/probe/color-sets-the-tms9918-colour-register.mjs` asserts a write to
register 7. That is still exactly right — `COLOR` is register 7 on both cards — but
the name and comments (lines 1–6, 30, 33, 46, 78, 86) say TMS9918.

## 3. Could — detect the card

Everything in §4 and §5 needs this first. For 2.x, detection is `STAT4` = `$AC`
plus `STAT6` b7, the built-in font bit of SPEC draft 0.5. `STAT5` (`$05`, the draft)
is recorded but gates nothing. A card that fails detection is not a PICOVDP, and
2.x has no path for it.

`ProbeVideo` (`Kernal.asm:1548-1579`) writes `$A5` to VRAM and reads it back, which
any card with readable VRAM passes. §16's probe tells the two apart: select
`STAT4` (write `$04` to register `$0F`) and read `$AC` from the status port.

- **Where the answer goes.** `HW_PRESENT` has no free bit (`BIOS.inc:64-71`), so it
  needs a new RAM byte — a card type, or a capabilities copy of `STAT6` (§6).
- **Order matters.** On a TMS9918A the probe's register write lands on register 7
  and changes the screen colours. Run it before `InitVideo`, which writes R7 = `$1F`
  anyway (`Kernal.asm:837`), and the damage is undone for free.
- **Put `STAT0` back afterwards** (§16's listing does), or the next status read
  returns `$AC` instead of the frame flag.
- **Verify in the emulator:** `--vdp picovdp` answers `$AC`, and `--vdp tms9918a`
  does not. Both are one `6502 run --headless` away.

## 4. Could — hardware scroll

§17's headline change. `VideoScrollImpl` (`Kernal.asm:252-336`) copies 23 rows of 40
through `SCROLL_BUF` — about 31,000 cycles, 30 ms at 1 MHz. Writing `L0SCRY` and
clearing one row is under 400 (§17 has the code).

The cost is a scroll origin that every cursor calculation has to fold in. The
places that assume the origin is zero:

- `VideoSetCursorImpl` (`Kernal.asm:183-224`), which computes `Y*40 + X` into
  `VID_CURSOR_ADDR`
- `VideoChroutImpl` and `VideoChroutRawImpl`, which increment `VID_CURSOR_ADDR`
  directly (374–376, 448–450), and their row and column limits (379, 385, 389, 411,
  414, 453, 458, 461)
- `VideoPutCharImpl` (243–247)
- `VideoClearImpl`, which zeroes the address (168–169) — and should reset the
  origin and `L0SCRY` with it

`VideoGetCursorImpl` is the exception: it returns `VID_CURSOR_X` and `VID_CURSOR_Y`,
which stay screen coordinates, so it needs nothing.

The name table address becomes `(origin + Y*40 + X) mod 960`; the origin moves by 40
per scrolled line and `L0SCRY` by 8, wrapping at 192 (§13 wraps the map at the
geometry's own height, which in Text is 192).

**Acceptance is structural.** 2.0 moves every `bios/` golden (Text mode with
per-cell colour, a new header, the hardware scroll), so no golden stays
byte-identical to compare against. The emulator adds `src/tests/goldens/Scroll.test.ts`
when it bundles 2.0: `scroll`'s `textGrid` equals `screenful`'s shifted up one row
with the new last row, and the index-frame rows of the unchanged text equal
`screenful`'s rows 8 pixels lower. `screen.text` already reads the name table as
displayed, with `L0SCRY` applied, so a hardware-scrolled console reads as it looks.

## 5. Could — interrupts, vertical blank, new entry points

**Port B for interrupt handlers.** The Kernal's `Irq` (`Kernal.asm:3159-3209`) never
touches the VDP and nothing in the BIOS brackets VDP work with `sei`/`cli`, so
there is no existing race to fix. The hazard is a *user* handler installed through
`IRQ_PTR` that talks to the card while foreground code is between the two writes of
a command. On the new card that handler can use `$9C02`/`$9C03` and never disturb
the foreground's pointer or flip-flop (§4). Worth writing down as the convention —
with the caveat from the top of this file that on today's card port B *is* port A.

**Vertical blank.** Nothing in the BIOS waits for a frame. `STAT0` b7 is set at the
end of every picture whatever `IRQEN` holds (§6) — and so was the TMS9918A's — so
a `WaitVBlank` entry point works on both cards.

**New Kernal entry points.** §17 suggests set mode, set a palette entry, set layer
scroll, load a tile set, place a sprite, enable a layer.

- The jump table (`Kernal.asm:25-100`) has 32 reserved slots, of which the planned
  v1.6 NVRAM save slots claim 6.
- The ABI is pinned in `tests/fixtures/jumptable.json`; new slots update it.
- Each entry point needs the detection result from §3, and returns carry set when
  there is no PICOVDP.
- The font load command of SPEC draft 0.5 (`FONT`, `$30`) is a Kernal entry of its
  own, `VdpLoadFont` in the BIOS plan: font ID in A, copy into `L0PAT`, wait for
  completion at the next vertical blank.
- BASIC has three video keywords today, `CLS`, `LOCATE` and `COLOR`
  (`BASIC.asm:273-275`, 8257–8285), and no `SCREEN`, `VPOKE` or `SPRITE`. Whether it
  should grow any is a design question this list does not answer.

## Bringing a changed BIOS back into the emulator

- 2.x is bundled as **`BIOS2.bin`**, at `assets/roms/BIOS2.bin` and
  `src/renderer/public/roms/BIOS2.bin`, and `BUNDLED_ROM.picovdp` points at it.
  `BIOS.bin` stays 1.6 for good, for the TMS9918A. `src/tests/BundledROM.test.ts`
  fails if either pair differs. Copy both.
- The PICOVDP fixtures in `src/tests/goldens/fixtures.js` switch ROM to
  `BIOS2.bin`. `src/tests/goldens/bios/` moves; `wizardslab/`'s frames must not
  (2.x's `KernalInit` leaves the card in the legacy submode). A change to how long
  `KernalInit` takes moves `vdp-layers/`, which scrolls every frame: at 2.0 it runs
  two frames ahead of 1.6. Run
  `npm run capture:goldens -- --check` first to see exactly what moved, and
  re-capture in a commit that says why.
- **`src/tests/goldens/tms9918a/` never moves for a 2.x change.** Those goldens pin
  the TMS9918A booting 1.6.
- `src/tests/BIOS.test.ts`, `HeadlessHost.test.ts` and `Snapshot.test.ts` boot the
  bundled ROM; a Kernal change that alters cycle counts to the prompt can move
  numbers there.
